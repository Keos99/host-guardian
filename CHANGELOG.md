# Журнал изменений

В этом файле документируются все заметные изменения проекта.

## [Не выпущено]

### Добавлено

- Добавлены оповещения в чат о событиях мониторинга (пакет `notification`):
  - сообщения отправляются при старте watcher, добавлении и удалении сервиса, недоступности сервиса, попытке запуска/рестарта, ошибке команды запуска, исчерпании лимита рестартов (требуется ручное вмешательство) и при восстановлении сервиса;
  - повторяющиеся алерты дедуплицируются: один эпизод недоступности дает одну пару сообщений «упал/восстановился», без спама каждые 30 секунд;
  - отправка асинхронная (отдельный поток `chat-notifier`), ошибки чата никогда не ломают цикл мониторинга и REST-операции;
  - транспорт — настраиваемый HTTP webhook (`notification.chat.url`), payload совместим по полям со старым SberChat-отправителем (`peer`, `status`, `message`, `url`); при пустом URL сообщения пишутся в лог приложения;
  - конфигурация в `application.yml`: `notification.chat.enabled` (главный выключатель), `url`, `peer`, `auth-header-name`, `auth-token`, `connect-timeout`, `read-timeout`.
- Добавлено управление оповещениями с dashboard:
  - глобальный переключатель «Оповещения: вкл/выкл» (хранится в БД, переживает рестарт; таблица `app_setting`);
  - переключатель оповещений для каждого сервиса в меню действий и чекбокс «Оповещения в чат» в форме сервиса (колонка `notifications_enabled`);
  - при `notification.chat.enabled=false` весь связанный UI скрывается, а API глобального переключателя отвечает 409.
- Добавлены REST-эндпоинты: `GET/PATCH /api/notifications`, `PATCH /api/services/{id}/notifications`; в ответ dashboard добавлен блок `notifications`.
- Добавлена Flyway-миграция `V3__notifications.sql` (колонка `notifications_enabled`, таблица `app_setting`).
- Добавлен параметр сервиса `executionPath`. Если он указан, команды старта и ручного рестарта выполняются из этого каталога; если не указан, используется прежняя логика выполнения.
- Добавлена обязательная команда старта `startCommand` для отслеживаемых сервисов. При рестарте сначала выполняется логика рестарта, затем сервис запускается через `startCommand`.
- Добавлен переключатель `manualRestartEnabled` для поля команды рестарта:
  - выключен: процесс сервиса ищется автоматически и завершается через `kill`;
  - включен: выполняется пользовательская команда `restartCommand`.
- Добавлен fallback на `kill -9`, если автоматическое завершение сервиса не укладывается в настроенный timeout.
- Добавлено определение PID сервиса при первой успешной проверке доступности. PID сохраняется в параметрах сервиса и выводится на dashboard.
- Добавлена проверка доступности по PID в дополнение к health-check и проверке процесса.
- Добавлен отдельный статус health-check на dashboard. Если URL health-check не указан, отображается `off`.
- Добавлена настройка timeout для SSH-команд в `application.yml` через `monitor.command.*`.
- Добавлена абстракция SSH-провайдера с двумя реализациями:
  - `system`, основанная на системной команде `ssh`;
  - `jsch`, основанная на библиотеке JSch.
- Добавлен выбор SSH-провайдера через `monitor.ssh.provider`.
- Добавлен параметр `monitor.ssh.strict-host-key-checking` для поведения JSch при проверке host key.
- Добавлены busy-состояния кнопок сохранения и операций с сервисами.
- Добавлены JavaScript-регрессионные тесты для обновления dashboard и busy-состояний кнопок.
- Добавлен JavaDoc для новых классов SSH-провайдеров и новых публичных методов конфигурации.

### Изменено

- Обновление данных dashboard сделано более отзывчивым. Блок dashboard обновляется отдельно и после операций с сервисами.
- Ответы операций с сервисами теперь запускают обновление данных, чтобы UI показывал актуальное состояние без ожидания следующего полного цикла polling.
- Логика recovery-команд изменена: если сервис не обнаружен, выполняется только `startCommand`; `restartCommand` выполняется только после нажатия restart при настроенном и неуспешном health-check.
- Документация README на английском и русском обновлена с учетом команд сервисов, PID, health-check, SSH-провайдеров, timeout и изменений базы данных.
- Колонки базы данных `restart_command` и `start_command` переведены с CLOB-маппинга на `varchar(4096)`.
- JPA-маппинг полей команд сервиса теперь использует ограниченные колонки `varchar(4096)` вместо `@Lob`.

### Исправлено

- Исправлен `PATCH /api/services/{id}/monitoring`: запрос падал с 500 (`LazyInitializationException` на lazy-прокси хоста при маппинге ответа после `save` detached-сущности). Методы-переключатели в `ConfigurationService` теперь транзакционные.
- Исправлено отображение health-check для сервисов без URL health-check. Поле больше не показывает `yes`; теперь отображается `off`.
- Исправлена совместимость PostgreSQL для колонок команд за счет удаления native CLOB из отредактированных Flyway-миграций.
- Добавлено регрессионное покрытие модели, чтобы поля команд не были снова замапплены как CLOB.

### Примечания по миграции

- Для изменения CLOB на `varchar(4096)` не добавлялась новая Flyway-миграция; существующие `V1__init.sql` и `V2__service_start_and_pid.sql` были отредактированы по запросу.
- Окружения, где эти миграции уже были применены, могут потребовать reset базы данных или Flyway repair перед запуском обновленной схемы.
